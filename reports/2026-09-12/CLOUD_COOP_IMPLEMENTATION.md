# 클라우드 저장·2인 협동 구현 현황

## 구현한 첫 단계

- 기존 SaveGame v1 포맷 유지. 그래픽 설정은 기존 기기 저장 유지.
- src/core/CloudSync.js: 서버 제공자와 분리한 저장 동기화 모듈.
- inspect는 서버 기록을 조회할 뿐 로컬 저장을 바꾸지 않는다.
- upload는 명시적으로 호출한다. 사전 조회 없이 업로드 불가.
- 서버의 원자적 revision 비교를 요구한다. 충돌은 자동 덮어쓰기하지 않는다.
- 응답 유실은 성공으로 표시하지 않으며 재조회 전 재시도 불가.
- check-cloud-sync.mjs: 두 클라이언트 충돌, 잘못된 데이터, 응답 유실, 중복 실행 검증 통과. 기존 저장·소스 검사 통과.

현재 모듈은 게임 UI에 연결되지 않았다. 온라인 저장·로그인·실제 2인 접속이 구현됐다는 뜻이 아니다. 모의 서버 테스트이며 실제 서버의 원자성/권한을 입증하지 않는다.

## 서버 연결 계약

remote.read(): 인증된 사용자 본인의 {revision, raw} 또는 null.
remote.compareAndSwap({expectedRevision,raw}): 서버 트랜잭션에서 현재 revision과 비교. 일치 시 새 revision과 saved, 불일치 시 conflict 반환. 최초 기록 생성도 expectedRevision=null 비교가 원자적이어야 한다.

서버는 요청의 사용자 ID를 신뢰하지 않고 인증 세션에서 결정한다. 저장 크기·전체 진행 스키마 검증, 사용자별 접근 권한, 요청 빈도 제한 필요. 브라우저 parseSave는 상위 포맷 검사이므로 서버 전체 검증을 대체하지 않는다.

클라우드에서 가져오기는 기존 세이브 백업 및 각 게임 구성요소의 검증을 끝낸 뒤 적용해야 한다. 최신 시각만으로 자동 선택하지 않는다. 진행 버전 충돌은 사용자가 양쪽 진행 요약을 보고 선택한다.

## 다음 구현 순서

1. 서버 프로젝트 선택 및 인증 방식 확정. 실제 키는 저장소에 넣지 않는다.
2. 인증/사용자별 저장/원자적 revision API 구축.
3. 설정의 계정 저장 화면: 마지막 동기화, 로컬 유지, 업로드, 가져오기 및 충돌 선택.
4. 기존 세이브 검증·백업·복원과 UI 연결. 두 브라우저 실제 저장 검증.
5. 범선 2인 방: 초대 코드, 참여/퇴장, 캐릭터 이동 동기화.
6. 균형 신전: 서버가 상자 소유권·배치·문 판정 결정. 클라이언트는 행동 의도 전송.
7. 끊김 시 상자 안전 반납, 재접속 스냅샷, 중복 행동 식별, 참여자별 보상 기록 검증.

## 협동 범위

최초 2인, 방장 진행을 기준으로 공간 구성. 참가자의 개인 완료 기록은 낮추지 않는다. 공유 퍼즐 저장과 개인 수첩·보상은 별개다. 개인 클라우드 저장 API에 프레임별 위치를 쓰지 않는다. 실시간 세션은 별도 통신과 권위 있는 상태 관리가 필요하다.

## 아직 필요한 정보

기존 서버 프로젝트 유무를 사용자에게 질문했다. 서버가 없으면 제공자 후보와 비용·운영 조건을 확인하고 연결 대상을 정한다. 현재 배포는 하지 않았다.

## 후속 구현

- 설정 화면에 ‘기록 파일로 보관’ 버튼 연결. 현재 captureProgress 전체를 JSON 다운로드하며 그래픽 설정은 포함하지 않는다.
- src/core/SupabaseSaveRemote.js: 인증된 Supabase SDK 클라이언트를 주입하는 adapter 작성. 아직 SDK·로그인·실서버 미연결.
- server/cloud-save.sql: 사용자별 RLS 읽기와 인증된 RPC 쓰기. INSERT 충돌/조건부 UPDATE로 revision 원자 비교. 클라이언트 직접 쓰기 금지.
- SQL은 실제 DB에서 실행/검증하지 않았다. 서버 전체 게임 스키마 검사·요청 제한은 아직 없으며 정식 운영 이전 필수다. 저장 데이터는 보상이나 협동 권한을 증명하지 않는다.
- 로그인 사용자 변경 시 기존 CloudSync 인스턴스를 폐기하고 새 사용자용 인스턴스를 만든다. 다운로드 데이터를 실행 중인 게임에 무검증 적용하지 않는다.
- 가져오기는 미구현: 각 구성요소의 독립 검증과 실패 시 원자적 복구부터 필요하다.

### 실제 연결에 필요한 것

Supabase 프로젝트 URL과 공개 publishable key. service_role 비밀키는 브라우저/저장소/대화에 넣지 않는다. 프로젝트 생성 후 전용 개발 DB에서 SQL 실행, 다른 두 사용자로 서로의 기록 접근 거부 검증, 같은 사용자의 두 세션 충돌 검증, 로그인 UI 연결 순으로 진행한다.

선정 근거: Supabase Auth와 사용자별 RLS를 함께 사용할 수 있다. 이메일 OTP/매직링크 인증을 지원한다. 아직 유료 서비스 생성이나 인증 메일 발송은 하지 않았다.

- https://supabase.com/docs/guides/database/postgres/row-level-security
- https://supabase.com/docs/reference/javascript/auth-signinwithotp

### 무무자리 프로젝트 연결 확인

2026-09-12 공개키로 Auth 설정 HTTP 200 확인. 이메일 인증 활성화, 회원가입 허용 상태. 프로젝트 URL/공개키를 SupabaseConfig.js에 추가했다. 로그인 UI에서 사용하는 연결은 아직 미구현이다.

게임 전용 mumuretro_player_saves 테이블은 REST 스키마 캐시에 없음(PGRST205). 기존 프로젝트의 다른 테이블을 변경하지 않도록 테이블/RPC 이름에 mumuretro_ 접두사를 사용했다. server/cloud-save.sql은 트랜잭션으로 묶었다. 공개키로 DDL을 실행할 수 없으므로 프로젝트 소유자가 SQL Editor에서 실행해야 한다. SQL 실DB 테스트 및 로그인 연결은 아직 남아 있다.

### SQL 설치 완료

무무자리 프로젝트 SQL Editor에서 이름 중복 없음(NULL/NULL) 확인 후 cloud-save.sql 실행 성공. 실제 DB 권한 조회: RLS=true, anon SELECT=false, authenticated 직접 INSERT=false, anon RPC EXECUTE=false, authenticated RPC EXECUTE=true. 기존 테이블 변경 없이 게임 전용 객체 생성. 로그인한 두 사용자 간 격리 및 실제 저장 충돌 테스트, 게임 로그인 UI 연결은 아직 남아 있다.
